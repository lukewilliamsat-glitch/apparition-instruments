# COMMAND and existing Admin

The existing authenticated Admin in main is substantial: Admin V2/V2.1 shell/overview, catalogue/specifications/settings, stock dialogs, assembly/kit definitions, Orders/fulfilment, Operations/News, CMS/Conjure, email/Aftercare/Studio. COMMAND is a separately isolated replacement candidate for selected catalogue/editor flows, not proof that every specialist workspace has been replaced or production integrated.

| Candidate | Implemented and evidenced | Boundary still open |
|---|---|---|
| COMMAND01 | Bounded catalogue summaries/detail, filters, stable selection and private/image minimisation; isolated Node/Chrome evidence | Fixture transport only; real authenticated read adapter not installed |
| COMMAND02 | Draft/review/discard, integer-pence and field authority validation, conflict/dirty-state protection | Protected stock/image/cost remain unavailable in generic editor; synthetic revision is not a deployed CAS column |
| COMMAND03 | Session/permission distinction, explicit synthetic bridge, stale-response guards, retained draft and unknown-save recovery | Default production-safe versioned writes unsupported; read fingerprint is not a DB revision; Afterimage closes original screenshot retention gap |
| COMMAND04 / IRONCLAD | Product/inventory/private cost/shared revision/receipt/audit atomicity; actor-bound replay; current authority; 61 real disposable PostgreSQL tests | Session_user/principal mapping and JSON fixture schema do not implement deployed Supabase JWT/auth.uid/admin_members/grants/RLS; all legacy writers must participate |
| NOCTURNE | Premium desktop/tablet/mobile catalogue/editor/status/dialog presentation; 47 new browser groups on inherited 119 | Owner UI approval and real backend integration remain separate; no PostgreSQL rerun in visual phase |

Six distinct levels: synthetic interface, synthetic transport and disposable PostgreSQL acceptance are evidenced. Real deployed schema, actual authentication/capabilities and production integration are not established by those three. A refreshed successful Pages build on main contains neither prototypes/command* nor their adoption route; no inference of COMMAND installation is permitted.

Financial boundaries: current private component_internal and existing Admin membership are useful starting points, not LEDGER's granular owner/finance capabilities. Orders/customer access, supplier costs and future profit projections must remain permission-scoped across list/detail/error/conflict/receipt/export/status. Existing main generic component save performs private-cost, optional inventory and product REST writes separately; stock updates predicate on old quantity. An IRONCLAD endpoint beside bypassing legacy writes is not sufficient.

## Targeted future security acceptance

1. Anonymous/customer/nonmember and read-only/stock-only/finance-only principals against every projection/RPC; no private costs, order ownership bypass or unauthorised enrolment.
2. Trusted actor/JWT/session/capability mapping, revocation during lock wait, expired sessions and same-actor status/replay; no client-claimed roles or production use of fixture trust auth.
3. All product/inventory/order/build writers share atomic revision/quantity invariants; crash/fault/replay/concurrent-write tests and exact durable receipt/audit binding.
4. Same operation/different payload and cross-actor receipt access denied; absent receipt remains unknown, not failure; no force-save/automatic duplicate submission.
5. SECURITY DEFINER owner/search_path/EXECUTE, grants/RLS/invoker-view composition, protected images/private costs, customer owner filters and data-minimised exports/caches.
6. Preserve all existing specialist Admin features and notifications while defining one shell/router/controller ownership model; test sign-out and stale responses without loading real customer data.

These are future tests, not demonstrated vulnerabilities or current execution authority. Source-proven architectural gaps (sequential writes versus desired atomicity) are distinguished from unknown deployed security. Exact bounded read-only Phase C precedes any real adapter/DDL proposal; backend modification and release need additional explicit approval.
