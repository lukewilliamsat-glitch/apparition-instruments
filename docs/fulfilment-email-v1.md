# Fulfilment corrections and email template parity V1

Admin Orders exposes Correct fulfilment stage for paid, eligible orders in an active later stage. A required reason and explicit confirmation record actor, old/new stage and timestamp in existing order history. The server locks and checks the displayed order version; stale, terminal, unreviewed partial-refund and pending/claimed-notification cases are rejected. Tracking, dispatch details, original history, finances, items and inventory remain intact. Normal forward transitions remain available; existing notification rows prevent replay when re-advancing.

Resend Dispatch Email is a distinct manual operation for a currently Dispatched order whose latest dispatch notification was accepted. The confirmation shows the current saved recipient and requires a reason. The server validates Admin membership, current order/version, eligible recipient, prior notification and unique operation identity, then freezes recipient/order snapshot in a new existing-ledger row linked to the prior notification. Concurrent intentions and duplicate retries cannot send twice. Original sends remain immutable. Failed, Unknown and Claimed attempts require review; neither the scheduler nor this interface automatically retries them. Completed/cancelled/refunded orders are not reopened for sending.

Mail server acceptance does not prove inbox delivery. eBay filtering may strip images or reject delivery. eBay dispatch uses the same approved branded renderer, logo, divider and illustration as website dispatch, with order-related eBay copy and without website/contact/tracking hyperlinks. Website output remains byte-identical. Admin Email Preview offers Website Dispatched and eBay Dispatched through the same renderer used for sending.

Backend: `fulfilment_email_v1` extends the existing notification ledger and adds authenticated Admin-only correction/resend RPCs. Service-only claims and audit outcome recording remain authoritative. The original-send partial unique index preserves existing uniqueness while allowing distinct resend rows; existing notification writers select/conflict against originals. No separate persistence or mail provider is introduced. Deployment checks use schema/permissions and unauthenticated rejection only; local fixtures and mocked SMTP cover business behavior.
