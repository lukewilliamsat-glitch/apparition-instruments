# Commerce Sentinel: staged acceptance and rollback

Base: `c8e94735f061dc4a25c32e3e77d401a2ae045bf7`. Migrations, in order: `20261116213239_commerce_ascendant.sql` and `20261116221000_commerce_sentinel.sql`. Commerce remains inactive in production. The fixture preview uses browser-local data only, and is not a Stripe or Supabase staging environment.

## Reservation and reconciliation contract

The service persists the original request before creating a Stripe session. The key is always `apparition-<order UUID>`. Two creation attempts at most, separated by at least ten seconds and within two minutes of reservation, share the same exact form body and expiry. The Stripe session expires at the saved 40-minute deadline. A same-tab retry reuses the intent ID; guests must complete a fresh Turnstile challenge each time, with the provider-verified hostname and action. The database serializes intake and limits it to two open checkouts per account, six open guest checkouts, twenty globally, 150 physical units held globally and 60 per order. The rolling minute limits are three per account, six guests globally and twelve total. Browser cancellation and elapsed time do not release uncertain holds.

The service-only recovery endpoint `commerce67-reconcile` requires its own server-held bearer. It looks up the attached session by ID, verifies an operator-supplied candidate ID with Stripe, or examines at most 100 Stripe sessions in the narrow dispatch interval and verifies the unique candidate by ID. The order UUID, reference, amount, currency, mode and provider identity must match. The endpoint never creates a session or pays an order. A verified paid session is attached and needs signed event replay to drive existing settlement. A verified expired/unpaid session releases stock; an empty or ambiguous list does not. The operator may explicitly release a stale *never-sent* reservation only when the database proves no durable send claim existed. Reservation diagnostics are Admin-only and omit provider session IDs, customer details and credentials. A failed provider response after a claimed send is intentionally not treated as proof that Stripe never created a session.

## Mixed basket and postage

Ordinary products can share a Commerce basket with bundles, measured sets or compatible add-ons. Any configured wiring kit in a basket with Commerce-specific selections still requires a separate checkout. The existing kit RPC validates the configuration and writes the order in one transaction. A future focused change must extract its trusted calculation and parts resolution as a side-effect-free function, then merge the result into the one order snapshot, one stock reservation and one Stripe session. Reusing a kit price supplied by the browser or combining two orders after payment is not a safe shortcut.

THE OVERSEER can extend `commerce67.delivery_pence(net_merchandise_pence)` to resolve an approved server-side delivery choice and persist its quote/version. It currently reads the existing GB rate and free-delivery threshold. Stripe continues to use the persisted order delivery amount. Legacy configured-kit postage remains unchanged; when unified, it should call the same provider.

## Gates before any production activation

1. Obtain a named isolated Supabase staging project and Stripe test or Sandbox access through a safe credential channel. Sanitize data, verify permissions and turn off real notification delivery. Add staging-only test-mode wiring for the existing live-prefix payment and fulfilment guards in the isolated stack; keep production strictly live-only. Run genuine test payments across the requested basket types, signed duplicate/out-of-order events, failure, refund, expiry, and operational attachment recovery. Validate Turnstile on the actual guest route and verify reservation-cap side effects for ordinary buyers.
2. Review exact SQL checksums, verify live schema hooks read-only, back up, and verify the current Cloudflare rollback target `7bfe4df0-02be-4bf2-9130-7e200be3688d`. Apply the additive migrations only under separately approved production authority, with Commerce disabled and no open Commerce reservations.
3. Deploy the compatible checkout, signed webhook and credential-protected recovery endpoint. Configure paid, expiry, and existing refund deliveries. Verify the reconciliation operator path, lock down the bearer, and keep notifications unchanged. At a controlled gate, reconcile old unpaid Stripe sessions and confirm there are no unreserved older checkouts that could compete for stock.
4. Configure the Turnstile secret, public widget key, signed event processing and protected recovery. Enable reservation-aware intake before enabling the database flag; publish the guarded Cloudflare storefront with matching flags. Run narrowly scoped acceptance with no unapproved live orders. Only then create an approved first offer.
5. Roll back by disabling new Commerce reservations and storefront activation, and restore the verified NIGHTFALL deployment. Keep payment, expiry and reconciliation available until every previously reserved order is resolved. Preserve audit rows, measured allocations and order snapshots; do not blindly release holds or drop tables.

No live Stripe configuration changes, real emails, production SQL or application publication are authorized in this rehearsal.
