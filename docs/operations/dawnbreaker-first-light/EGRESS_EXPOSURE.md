## Historical measurements and their scope

V1 records one controlled live HTTP comparison using the same public key and gzip preference: full public projection **11,946,961 raw JSON / 9,007,039 encoded body bytes** versus technical image-free projection **8,843 / 1,875 bytes**, both 14 rows. Headers/TLS excluded; an initial Node attempt timed out and curl completed the comparison. V1 separately records JSONB serialisations of 11,947,341 /9,195 bytes: do not mix them with HTTP bytes. V2 reports a server-side inventory of six embedded PNGs, **8,953,356 decoded bytes**, among 36 components/14 public rows. No new image retrieval or provider query occurs here. These dated counts are not current inventory.

NIGHTFALL's synthetic 500-product body reductions and warm-cache results are isolated workload evidence, not monthly billing savings. Multiplying the historical full encoded body by 30 hypothetical daily runs gives **270,211,170 encoded body bytes** for that catalogue response alone; a daily month has 28–31 runs and actual generator filtering/content/encoding differs. This is a scenario, not a measured consumption total or a reliable upper bound. Visitor/refresh/admin paths can multiply exposure independently. Git source and GitHub runs cannot apportion the historical allowance exceedance.
