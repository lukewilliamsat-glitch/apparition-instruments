Separately authorise an isolated, backend-free **publication and restoration rehearsal**, not a live recovery experiment:

1. Pin current source, ANCHOR inventory/digest and the intended candidate overlay; first implement/verify package validation and publish/restore control flow with wholly synthetic payloads. No production credential, API or deployment call in this stage.
2. Define a trusted read-only active-deployment association method using supported GitHub metadata or redacted owner evidence. Source/run success alone is insufficient. If supported access cannot establish the target/current relationship, retain UNKNOWN; no browser crawl or new artifact download follows automatically.
3. Only if separately authorised for a named necessity, materialize the already-retained exact original once with explicit byte/hash/safety/access limits. No additional public artifact search; no image transformation/publication. Offline browser rendering of archived images would itself require that later scope's explicit permission.
4. Prepare a complete manifest-bound release assembly and full previous-payload restoration package; retain all unchanged generated products/CMS/News/images. No hidden generator or backend access.
5. Design/test a supported publication-only candidate route that consumes the approved complete payload, rejects drift/partial files, shares `pages` concurrency, checks competing publishers and preserves/attests rollback. No production workflow edits under FIRST LIGHT; future candidate route/adoption authority must be explicit. Synthetic tests cannot prove actual GitHub deployment capability.

A real upload/deploy/rollback test, active-site probes, main/workflow adoption, production credentials or live browser acceptance need a new exact release authorisation; do not claim production restoration was tested merely from an offline harness.
