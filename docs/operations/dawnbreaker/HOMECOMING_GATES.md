## Conditional release decision tree

1. **Can a complete authentic active payload be recovered through a separately approved cloud mechanism?** Require exact deployment/run/source association, full per-file path/size/hash inventory, payload/archive digest and generation provenance. If no, HOLD. A separately authorised rebuild/adoption may be proposed with explicit provenance limitations, approved backend exposure and complete content review; do not reconstruct/publish under this runbook authority.
2. **Is a complete previous payload retained and independently readable for rollback?** Require durable approved retention beyond ephemeral artifact expiry, verified original bytes and tested exact restoration. If no, HOLD. A CSS Git inverse is not a full site rollback.
3. **Can the complete payload be assembled without hidden generation?** Overlay only the exact reviewed CSS and any separately reviewed required fingerprint references. Verify every other byte/path against the independent inventory; reject missing/extra CMS/product/assets and drift. If generation is required, separately approve its exact inputs, backend calls/budgets and output verification. No current workflow marker makes it backend-free.
4. **Is a safe publication-only route implemented and independently tested under separate authority?** It must consume the verified complete payload, retain rollback, share Pages concurrency, reject source/deployment drift and upload exactly the approved artifact. Existing production workflow is unsuitable as a backend-free CSS bypass. Do not edit it here.
5. **Are owner release approval and bounded post-deployment/rollback criteria explicit?** Only then may a separate mission publish. Supabase restoration, Phase B/C success or automated fixture acceptance does not grant this approval.

## Future release/rollback acceptance contract

Before a write, recheck refs, active deployment identity and no conflicting queued/in-flight publisher; record exact source, CSS, complete manifest, assembled artifact and prior rollback identities. Approve specific live URLs/devices, request count/byte/time limits and backend exposure. No broad browser crawl or checkout/payment action is implicit.

After publication, separately authorised checks must confirm served payload/release association, CSS digest/fingerprint, headline layout and responsive routes, catalogue/product/CMS/asset completeness and essential accessibility within scope. Unexpected content loss, bad CSS, headline collapse, unreachable essentials, unapproved backend traffic or other agreed material regression triggers restoration of the **entire retained prior payload** through the approved route, then independent verification. Do not reset frozen refs, roll back business data or delete immutable assets. If no proven restoration path exists, do not begin publication.

The smallest safe release is therefore not a one-file main push today. It is a complete attested payload plus exact overlay, verified rollback and separately approved publication route. These missing dependencies remain documented blockers.
