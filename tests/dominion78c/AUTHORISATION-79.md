# DOMINION 79 isolated integration

The implementation is under `tests/dominion78c/` on `engineering/dominion78c-foundations`. The fixtures require a loopback PostgreSQL 17.6 database named `dominion79_fixture` and refuse any other database name before creating objects. CI installs the accepted A+B+C SQL from checksum-verified sources; it has no deployment job, provider keys or production database access. The browser composes only a local fixture against the verified Release C shell and blocks all real network calls.

Native scenarios: configured kit / assembly / item saved BOM → hold → existing paid writer → inventory and receipt provenance → one pack/cost event; eBay fixture matching an existing synthetic external order; actual IRONCLAD procurement receipt; an explicit measured set with competing stock and quality holds; guarded cancellation/expiry with legacy checkout fallback; duplicate payment, procurement, packing and provider evidence. JavaScript tests cover provider envelopes and fault injection, and Chromium verifies session denial, the two authenticated fixture workspaces, 390 px navigation, label and parcel review, sign-out/re-entry, and a single shared Admin module URL.

For a future rollout, use one stock transition owner. Keep the current checkout as fallback; do not turn on two counter systems. Freeze new reservations before rollback, preserve evidence and fulfil/expire every confirmed in-flight hold against authoritative provider state. Restore the accepted reservation projection and remove only the experimental guards once no live holds rely on them. Existing order, stock, cost and payment history must survive any rollback. This is a rehearsal/activation plan, not production SQL approval.
